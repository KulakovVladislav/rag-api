# Defense: FSM статусов ingestion и BackgroundTasks

> **Предмет разбора:** статусы `processing` → `completed`/`failed` и запуск обработки через `BackgroundTasks`.
>
> **Код для разбора:** `app/api/documents.py:36–42`, `app/api/documents.py:50`, `app/api/documents.py:57–66`,
> `app/api/documents.py:76`, `app/services/document_service.py:93–104`, `app/database/models.py:15`.

---

## Контекст

Если что-то ломается, например, на середине процесса обработки документа, то он остается в статусе processing.

**Ответ:**

Если процесс `uvicorn` умирает во время обработки, например во время `await get_embeddings`, документ остается в статусе
`processing`, потому что до изменения на `completed` код еще не дошел. `completed` устанавливается позже, а при обычном
исключении есть отдельная ветка перевода в `failed`.
`app/api/documents.py:50`, `app/services/document_service.py:63`, `app/services/document_service.py:74–81`,
`app/services/document_service.py:93–104`

### Как запускается обработка

**Ответ:**

После создания документа ему устанавливается `status="processing"` и он сохраняется в БД. Затем обработка добавляется
через `background_tasks.add_task(...)`, после чего запускается `process_document_background`.
`app/api/documents.py:46–56`, `app/api/documents.py:76–81`

## Варианты

Какие ещё способы можно использовать для обработки документов и управления их статусами?

### Вариант 1

**Ответ:**

отдельный воркер, который Забирает задачу из очереди. и работает с ее обработкой он знает, что нужно обработать
документ,
так как API при создании документа отправит задачу с document ID в очередь

### Вариант 2

**Ответ:**

Отдельный воркер, который будет смотреть, если есть задачи со статусом процессинг, которые довольно долго не менялись. И
если есть, то он будет пытаться продолжить или перезапустить обработку.

---

## Выбор

### Что делает код сейчас

**Ответ:**

Сейчас используется FastAPI `BackgroundTasks`: документ сначала создается со статусом `processing`, затем в background
task выполняется обработка. При успешном завершении статус меняется на `completed`, а при обычном исключении — на
`failed`.
`app/api/documents.py:46–56`, `app/api/documents.py:76–81`, `app/services/document_service.py:45–47`,
`app/services/document_service.py:74–81`, `app/services/document_service.py:93–104`

### Почему выбран этот подход

**Ответ:**

Первое. Этот вариант довольно легко внедрить. Для него не нужны отдельные воркеры или процессы. И он отлично подходит для довольно небольшой нагрузки моего проекта.
---

## Цена

* Утрата автоматического продолжения обработки после падения процесса: документ может остаться в `processing`, а
  повторный `POST` с тем же content получит `409`, потому что существующий документ уже найден по hash.
  `app/api/documents.py:34–42`, `app/api/documents.py:76–81`

* Если приложение вырастет, то нагрузка кратно увеличится. Эти задачи у меня выполняются внутри того же приложения. Если
  их станет много и не станут тяжелыми, то нагрузка вырастет. Появится конкуренция задач. нету сейчас контроля очереди и
  масштабирование возможности для масштабирования
