# Defense: Observability

## Решение: Передача `request_id` в каждую строку лога

### Контекст

Без какого-либо опознавательного знака на логах все запросы вперемешку и непонятно на каком именно произошла ошибка.
Решается добавлением request ID индивидуального знака для каждого лога.

плохой вариант:
14:03:02 ошибка при чтении кэша
14:03:02 ответ отправлен

Хороший вариант:

14:03:02 ошибка при чтении кэша request_id=a1
14:03:02 ответ отправлен request_id=a1
14:03:03 ошибка при сохранении документа request_id=b2

### Варианты

#### Вариант 1. Передавать `request_id` вручную в каждый лог

`request_id` добавляется в каждый вызов логирования как аргумент. Плюс в том, что всё явно, но минус в том, что нужно не
забывать добавлять ID. Если забыть, потенциально важная запись останется без метки.

#### Вариант 2. Использовать `LoggerAdapter`

По сравнению с первым вариантом, `LoggerAdapter` позволяет объединить логгер и `request_id` в одном объекте, не добавляя
ID вручную в каждый вызов логирования. Минус в том, что вложенные функции, которым нужно логировать с тем же контекстом,
должны получить этот адаптер, то есть его придётся передавать дальше.

#### Вариант 3. Использовать `ContextVar` и фильтр логирования

В этом проекте middleware сохраняет ID каждого запроса в `ContextVar`. Код внутри запроса использует свой контекст, а
фильтр достаёт из него ID и добавляет к записи лога. Параллельные запросы используют свои значения.

Плюс в том, что не нужно передавать ID вручную, в том числе для логов библиотек. Минус в том, что за пределами
соответствующего контекста ID может быть недоступен, например в фоновой задаче, другом потоке или процессе.

### Выбор

Выбран вариант 3. Запрос проходит так: middleware устанавливает ID (`middleware.py:17–20`), далее выполняется код в
`search`, `documents` и сервисах, а затем формируются записи логов.

Логи пишет не только мой код, но и библиотеки (SQLAlchemy, uvicorn), код которых я не меняю. Поэтому вариант 3 подходит
проекту: фильтр добавляет ID к записям без необходимости изменять места логирования в моём коде и библиотеках.

Вариант 1 отклонён, потому что ID пришлось бы передавать вручную в каждый вызов логирования, и его легко забыть. Вариант
2 отклонён, потому что адаптер пришлось бы передавать во вложенные функции, которым нужен тот же контекст.

Фильтр на handler достаёт ID из `ContextVar` (`logging.py:11–15`), подключается к обработчику на `logging.py:51`, а сама
переменная объявлена в `context.py:3`.

### Цена

- **Фоновая задача:** `request_id` приходится передавать явно из `documents.py:72–79` в `process_document_background()`
  (`document_service.py:45`), чтобы не зависеть от неявного распространения `ContextVar`. Точный порядок сброса
  контекста и запуска задачи не проверен.

- **Входной заголовок:** `middleware.py:17` принимает `X-Request-ID` от клиента без проверки длины и уникальности.
  Клиент может повторно использовать чужой ID, из-за чего логи разных запросов будет сложнее различать.

- **Читаемость логов:** в `search.py:130` `request_id` не виден в вызове `logger.info()`, потому что автоматически
  добавляется фильтром (`logging.py:11–15, 51`). Это упрощает логирование, но связь между вызовом логгера и появлением
  ID неочевидна без знания настройки фильтра.
