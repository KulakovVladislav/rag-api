# Defense: Observability

## Решение: Передача `request_id` в каждую строку лога

### Контекст

Без какого-либо опознавательного знака на логах все запросы вперемешку и непонятно на каком именно произошла ошибка.
Решается добавлением request ID индивидуального знака для каждого лога.

плохой вариант:
14:03:02 ошибка при чтении кэша
14:03:02 ответ отправлен

Хороший вариант:

14:03:02 ошибка при чтении кэша request_id=a1
14:03:02 ответ отправлен request_id=a1
14:03:03 ошибка при сохранении документа request_id=b2

### Варианты

#### Вариант 1. Передавать `request_id` вручную в каждый лог

`request_id` добавляется в каждый вызов логирования как аргумент. Плюс в том, что всё явно, но минус в том, что нужно не
забывать добавлять ID. Если забыть, потенциально важная запись останется без метки.

#### Вариант 2. Использовать `LoggerAdapter`

По сравнению с первым вариантом, `LoggerAdapter` позволяет объединить логгер и `request_id` в одном объекте, не добавляя
ID вручную в каждый вызов логирования. Минус в том, что вложенные функции, которым нужно логировать с тем же контекстом,
должны получить этот адаптер, то есть его придётся передавать дальше.

#### Вариант 3. Использовать `ContextVar` и фильтр логирования

В этом проекте middleware сохраняет ID каждого запроса в `ContextVar`. Код внутри запроса использует свой контекст, а
фильтр достаёт из него ID и добавляет к записи лога. Параллельные запросы используют свои значения.

Плюс в том, что не нужно передавать ID вручную, в том числе для логов библиотек. Минус в том, что за пределами
соответствующего контекста ID может быть недоступен, например в фоновой задаче, другом потоке или процессе.

### Выбор

Выбран вариант 3. Запрос проходит так: middleware устанавливает ID (`middleware.py:17–20`), далее выполняется код в
`search`, `documents` и сервисах, а затем формируются записи логов.

Логи пишет не только мой код, но и библиотеки (SQLAlchemy, uvicorn), код которых я не меняю. Поэтому вариант 3 подходит
проекту: фильтр добавляет ID к записям без необходимости изменять места логирования в моём коде и библиотеках.

Вариант 1 отклонён, потому что ID пришлось бы передавать вручную в каждый вызов логирования, и его легко забыть. Вариант
2 отклонён, потому что адаптер пришлось бы передавать во вложенные функции, которым нужен тот же контекст.

Фильтр на handler достаёт ID из `ContextVar` (`logging.py:11–15`), подключается к обработчику на `logging.py:51`, а сама
переменная объявлена в `context.py:3`.

### Цена

- **Фоновая задача:** `request_id` приходится передавать явно из `documents.py:72–79` в `process_document_background()`
  (`document_service.py:45`), чтобы не зависеть от неявного распространения `ContextVar`. Точный порядок сброса
  контекста и запуска задачи не проверен.

- **Входной заголовок:** `middleware.py:17` принимает `X-Request-ID` от клиента без проверки длины и уникальности.
  Клиент может повторно использовать чужой ID, из-за чего логи разных запросов будет сложнее различать.

- **Читаемость логов:** в `search.py:130` `request_id` не виден в вызове `logger.info()`, потому что автоматически
  добавляется фильтром (`logging.py:11–15, 51`). Это упрощает логирование, но связь между вызовом логгера и появлением
  ID неочевидна без знания настройки фильтра.

## Решение: Разделение liveness и readiness probes

### Контекст

В проекте должно быть две отдельные проверки состояния приложения. Первая — проверка, жив ли процесс, то есть не завис
ли он. Если завис, значит, его нужно перезапустить.

Вторая — проверка готовности. Если всё готово, можно приступать. Если проверка провалена, процесс не трогать и трафик не
слать. При этом полностью перезапускать процесс мы не будем.

Если Postgres перезапускается 20 секунд, то проверка `live` должна продолжать проходить, потому что сам процесс
приложения жив и не завис, а `ready` должна проваливаться, чтобы трафик не отправлялся в приложение до восстановления
базы данных. Если же перезапустить приложение при отказе Postgres, это не решит проблему, так как база данных всё равно
будет недоступна.

### Варианты

**A. Одна проба, всегда `200`.**

Самый простой вариант. Его единственный плюс — простота и отсутствие нагрузки. Но минусы перевешивают этот плюс, так как
он не обнаруживает отказ зависимости, и трафик может пойти в сломанное приложение.

**B. Одна глубокая проба на всё.**

Плюс в том, что это самый глубокий способ и он видит любые отказы. Минусы: ресурсозатратность, так как при каждой
проверке выполняются тяжёлые операции, и возможность перезапуска даже здорового процесса при отказе зависимости.

**C. Две пробы: `live` без зависимостей и `ready` с ними.**

Плюс в том, что разные пробы позволяют по-разному реагировать на отказы: перезапускать зависший процесс или не
отправлять трафик в приложение, которое не готово к работе.

Минус: если ready проверяет зависимости, то при отказе одной из них приложение перестанет считаться готовым и перестанет
получать трафик, хотя сам процесс останется живым. Нужно определить, какие зависимости действительно критичны, чтобы
отказ некритичной зависимости не приводил к исключению приложения из балансировки.

**D. `ready` проверяет только критичные зависимости.**

Плюс: `ready` проверяет только критические зависимости, и если откажет что-то не столь важное, то всё останется в
балансе.

Минус: нужно определить, какие зависимости критические, и отказ каких-то незначительных зависимостей будет менее
заметен.

### Выбор

Сейчас в проекте реализован вариант C, когда `live` проверяется без зависимостей (`app/api/system.py:45`), а `ready`
проверяет зависимости (`app/api/system.py:50`). Я считаю, что это хороший вариант. Главное — грамотно подобрать, какие
зависимости критичны, а какие нет.

В проекте проверяются три зависимости: база данных, Redis и Embedded Model (`app/api/system.py:51–55`). Пока оставляем
вариант C, потому что Redis используется не только при поиске, но и при загрузке документов для инвалидации поискового
кэша (`app/services/document_service.py:81`).

Если `invalidate_search_cache()` выбрасывает исключение, общий обработчик вызывает `db.rollback()`, который отменяет
незакоммиченные изменения, а затем пытается установить документу статус `failed`
(`app/services/document_service.py:93–104`). Получается, сбой Redis может привести к неуспешной загрузке документа, хотя
сама проблема возникла при инвалидации кэша. Поэтому в текущей реализации Redis влияет на успешную обработку документов,
и считать его некритичной зависимостью пока нельзя.

У варианта C есть недостаток: при отказе Redis приложение может перестать получать трафик, даже если `/api/search`
способен продолжать работу без кэша. Это ограничение текущей реализации, которое нужно зафиксировать в
`Known limitations`.

Почему не одна проба? Всегда 200 — это слишком простой и неглубокий вариант. Не подходит.

Если поставить одну глубокую пробу на всё, этот вариант уже лучше, но он ресурсозатратный. Кроме того, отказ зависимости
может привести к перезапуску здорового процесса, хотя проблема заключается не в самом приложении, а во внешней
зависимости.

### Цена

**1. Зависший Redis**

При зависшем Redis ждёт только `check_redis`. `check_database` в этом сценарии отвечает быстро, поэтому десять секунд из
двух последовательных ожиданий по пять секунд здесь не получается.

В актуальной документации `redis-py` для `socket_timeout` указано значение по умолчанию 5 секунд. В проекте этот
параметр явно не задан (`app/core/redis.py:9–13`), поэтому это значение по документации, не измерено в проекте.

`timeout` в `docker-compose.yml:14` равен 3 секундам. Он истекает раньше, чем пятисекундный таймаут сокета, поэтому
Docker не дожидается ответа проверки и фиксирует попытку healthcheck как неуспешную. `interval: 3s` в
`docker-compose.yml:13` задаёт интервал между запусками проверок, а не время ожидания ответа.

**2. Проверка модели эмбеддингов**

Проба запускается каждые 3 секунды (`docker-compose.yml:13`) и каждый раз кодирует строку реальной моделью. Это
ресурсозатратно, но точное время `encode` не измерено. Если модель занята обработкой документов (ingestion), проверка
может выполняться дольше обычного. При превышении `timeout: 3s` в `docker-compose.yml:14` Docker сочтёт проверку
неуспешной, даже если сам процесс приложения остаётся живым.

**3. Синхронные проверки в асинхронной функции**

`check_database` и `check_redis` синхронные внутри `async def system_ready`. Пока `check_redis` ждёт ответа, блокируется
event loop. В это время задерживаются и другие запросы, которые должен обработать этот event loop, включая `/api/search`
и запросы на загрузку документов.

При этом генерация эмбеддингов в `app/services/embedding_service.py:21` выполняется через `run_in_threadpool`, поэтому
сама эта операция не блокирует event loop. Однако запрос всё равно ждёт завершения генерации эмбеддингов.
